# G03 试玩与课堂演示

主展示案《雾港停电案》从一条目击证词开始。玩家需要区分两座钟核对后的时间、背心与钥匙的领用记录，以及审计员被阻止递交的材料。辅助提示可以整理这些线索，最后的指控由玩家提交。

## 开始前

1. 启动 FastAPI 和 React，打开 `/library`。演示前用 Mock 跑一次下方流程，检查浏览器能加载两个案件。[运行说明](../README.md)
2. 准备两个独立的浏览器会话，例如一个普通窗口和一个隐私窗口。首位玩家开案，在右侧「调查记录」点击「邀请玩家」。第二位在另一个窗口打开邀请链接，输入姓名并选择「加入调查」。
3. 准备真实模型对照时，在服务端配置 `deepseek-flash`，用同一组固定情境获取实际决策记录。现场若用 Mock 或发生规则回退，保留界面显示的来源标识。[验收与复现](../ACCEPTANCE.md)

## 雾港停电案完整路线

以下问法用于复现。换一种自然语言表达也可调查。即便委托被拒，仍可直接向获准披露的角色询问，并检查缺少的前置条件。

| 操作 | 可据此继续调查 |
| --- | --- |
| 选择《雾港停电案》并开始。先问阮岑「有人来问过西门出入吗？」 | 建立联络前的对照。直接改问「昨晚西门谁进过仓库？」时，门卫可说出自己看见的背心与时间。 |
| 选宋屿，说「帮我去问问门卫昨晚谁进过仓库」。等待受理和回报，再问阮岑「是谁来问过西门出入？」 | 回报应归于门卫的陈述。阮岑能从自己收到的联系中确认是谁来问。他没看清脸，背心号码仍需要核对。 |
| 给林遥出示「监控校时便条」，再向宋屿询问「有人提过监控时间的误差吗？」 | 林遥可按案情把观察转达给宋屿。从宋屿的回应分辨他采信了转述还是建议核实。 |
| 请林遥「替我核对这两份证词」 | 校时和复电日志把监控显示的 21:54 归为北塔标准钟 21:46。此处依据是记录读数。 |
| 问阮岑「可以帮我翻翻七号背心的领用表吗？」。如果对方要求工单，在原对话框出示「停电检修工单」以后再问。 | 领用表把编号 07 的背心和过磅间备用钥匙归到同一名领用人。 |
| 给宋屿出示「半张过磅联」，再说「请帮我核查夜航四号的送审底单」 | 审计组的待交件登记提供次日上午的递交安排和争议事项。成功核查后，调查席可以取得登记副本。 |
| 在「调查记录」使用「总结线索」「下一步提示」和「更新复盘」，把待核实的说法和记录填进自己的推理笔记 | 复盘按记录展示当时可见的进展。在回报旁点「公开回报」，另一位玩家可在自己的调查记录中查看这条公开内容。 |
| 打开「提交推理」，自主选择嫌疑对象和作案动机，按「确认选择」和「提交最终推理」 | 对照时间、领用记录以及账目矛盾。失败后可继续调查。完成结案后可选择「查看结案解释」。 |

<details>
<summary>教师用结案提要</summary>

雾港正确指控为罗钧，动机为掩盖虚报货重。阮岑能作证的是入库时刻和衣着。在时钟对齐后，背心与钥匙的领用记录把身份和进入过磅间的条件连在一起，半张过磅联与待交件登记解释了审计员遭遇的原因。

宫廷案的正确指控为武惠妃，动机为掩盖武氏家族贪墨军饷。御史台副册保留了「武氏军饷核查」索引与签押缺失的登记。玩家需要把副册、角色陈述和密室通道的证物合起来推理。

## 8 分钟课堂脚本

| 时间 | 现场操作 | 请同学核对 |
| --- | --- | --- |
| 0:00–0:45 | 说明雾港案的目标，发邀请，第二位同学加入 | 两个窗口如何确认是同一局，并持有不同的调查身份？ |
| 0:45–2:00 | 第一位询问阮岑的联络状态，委托宋屿，再向阮岑追问来源 | 委托发生前后，哪一条可见信息变了？门卫的观察能确认到什么程度？ |
| 2:00–3:00 | 第一位只共享一条回报，第二位在自己的窗口查看，再检查自己的笔记和复盘 | 对方收到的是哪一条？第一位的其他对话是否仍在自己的席位内？ |
| 3:00–4:30 | 分头出示校时便条与停电工单。各自由出示材料的席位核查对应记录，再交流八分钟差值、背心和钥匙 | 哪一步解开了前置条件？换成无权限的 NPC 会怎么回应？ |
| 4:30–6:00 | 出示过磅联，核查送审底单，再看提示和关键节点 | 哪些是已核对的记录？哪条信息是带来源的个人主张？ |
| 6:00–7:00 | 由玩家提交指控和动机，按需要展开完整解释 | 结案的判定依据是什么？哪些显示内容属于事后解释？ |
| 7:00–8:00 | 用宫廷案的同一份秘录记录对比公主、御史、张昌宗的玩家可见结果，并展示两案的自动评测 | 哪一处是共用机制？哪些差异由角色、行动和故事数据产生？ |

宫廷案的短对照可在演示前备好。把「遗失的宫闱秘录」给以下三位人物看，并分别说「请帮我核对宫闱秘录的借阅登记」。

| 人物 | 依据 | 可见后果 |
| --- | --- | --- |
| 太平公主 | 想查清秘录去向，认识并信任御史，拥有联络途径 | 联系御史，带回一条有来源的口头说明。 |
| 御史大夫 | 要以原始记录为准，知道副册的内容并有查阅权限 | 亲自核查副册，带回一条已核查的材料记录。 |
| 张昌宗 | 更关心香囊领用，缺少登记的知识和权限 | 拒绝查阅登记，并建议找保管人。 |

对照自主联系时，给公主出示秘录前后各问御史一次「有人查过秘录登记吗？」，再问「谁来问过秘录登记？」。雾港的两组模拟使用同一句仓库委托。阮岑信任宋屿时可给出自己的目击内容。降低信任后，回报只说明宋屿联系了阮岑、对方未提供这件事的内容。玩家仍可亲自向阮岑询问。Mock 路径可重复，真实模型的行为与运行指标以对应评测记录为准。[评测情境](../tools/npc_scenarios.json) · [本次验收](../ACCEPTANCE.md)

## 课程目标映射与待确认项

仓库中可核对的目标来自 G03 主任务和之前的实现记录。当前映射用于课堂讲解，课程评分细则与达标认定由教师确认。[G03 主任务](https://github.com/bingc11/g03-dynamic-mystery/issues/4)

| 课程能力或交付方向 | 当前作品中的对应内容 | 变化或待确认 |
| --- | --- | --- |
| 故事设计与可玩的调查体验 | 两案置于原有桌面调查面板，玩家经口供、材料和核查连接到固定真相 | 主展示选择雾港案。宫廷案用于验证同一套机制能承载不同故事。 |
| 交互中的自主角色与协作 | 角色基于权限、知识和关系决定接受、拒绝或联系他人。两席位通过显式共享分工 | 玩家社交和匹配不属于本阶段范围。 |
| AI 能力与约束 | 真实模型在候选范围内提议，规则引擎持有事实、权限和结案条件 | 教师可选择查看真实模型证据与确定性对照，不同运行应保留各自标签。 |
| 工程与可重复研究 | 自动情境、投影隔离、重启恢复、模型失败回退与记录样例 | 评估样本范围、展示时长要求与评分权重请教师按课程标准确认。 |
| 表现媒介和扩展 | 本阶段复用 React 与 FastAPI，保留记录复盘和双人桌面协作 | 若课程另有 Unity、2D/3D 或特定美术形式要求，需要教师确认是否接受桌面呈现。 |
| 授权和材料 | 教学改作保留上游许可、署名及来源。运行模型和评测证据另行标明 | 课堂以外的公开分享按仓库许可审阅。[仓库许可](../LICENSE) |
