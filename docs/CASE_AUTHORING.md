# 新案件接入指南

案件由服务端规则数据和原剧本库的展示数据组成。《雾港停电案》与《深宫血色：玉玺谜云》共用同一套身份验证、角色决策、动作裁定和复盘机制。[雾港规则数据](../api/npc_cases/harbor_blackout.json) · [宫廷规则数据](../api/npc_cases/example_4.json)

## 接入顺序

1. 复制相近的案情 JSON 到 `api/npc_cases/`。文件名和 JSON 的 `id` 一致。服务端用这个 ID 读取配置。
2. 编写公开案情、人物介绍、证物呈现和传统剧本库入口。新建一个标有 `npcManaged: true` 的 Script 数据文件，并在 `getExampleScripts()` 增加入口。角色名字、证物 ID、案件 ID 要与服务端对应。展示数据使用玩家开局便能知道的内容。[雾港展示数据](../web/src/data/harborBlackout.ts) · [剧本入口](../web/src/types/script.ts)
3. 先构建一个能自主进行的短路线。让角色说清自己经历过什么，再让一个具备权限的角色去核查物件。加入一个受限或不可达对象，给玩家可用的替代调查路径。把可共享的材料和首次获得的时刻写入测试情境。
4. 运行单测和场景模拟，用新会话走一次从开案到提交推理的完整路线。改动已加载的 JSON 后，重启 API 并开新局测试。保存上一局和模型评测记录时，记录所用的案件版本或提交号。[验收命令](../ACCEPTANCE.md)

可先在仓库根目录对照两套可重复路径。

```sh
python -m unittest discover -s tests -p test_npc_case_data.py -v
python tools/simulate_cases.py --driver mock --output /tmp/g03-eval-mock.json
python tools/simulate_cases.py --driver rules --output /tmp/g03-eval-rules.json
```

新案的评测场景与两套现有用例写在同一个场景文件。真实模型比较使用同一组输入和显式调用上限，命令见验收记录。[评测情境](../tools/npc_scenarios.json)

典型的同类案件需要一个服务端 JSON、一个前端展示数据文件和一处剧本库注册。对应场景配置与断言随案补齐。引入全新的动作类型或证物机制时，应先描述新增规则与验收条件，再修改引擎。

## 配置表

| 字段 | 应填写的内容 | 校验重点 |
| --- | --- | --- |
| `id`、`title` | 稳定案件 ID 与玩家可见标题 | 文件名、前端路由和案例数据一致。 |
| `truth` | 唯一正确的嫌疑对象、动机、结案解释与固定时间线 | `suspect`、`motive` 必须是 `verdict` 中玩家实际可选的值。时间线用 `{when, event}` 按故事顺序填写。`clues` 可引用关键证物或记录。 |
| `verdict` | `suspects` 和 `motives` 选项 | 用合理的错项检验推理。不能把任何选项都当作正确动机。 |
| `roles` | 身份、动机、目标、关系与信任，初始知识、可披露记录和核查能力 | `knowledge`、`disclosure`、`verify` 引用有效记录。角色有权披露才可转述。 |
| `topics` | 主题名、口语别名和可用候选行动，可写一条可执行的 `hint` | 别名匹配玩家理解的调查对象。提示使用玩家知道这项主题后便可采取的行动。 |
| `records` | 可核查材料、亲历陈述和传闻，标记 `kind` 为 `fact` 或 `claim` | 可用 `basis` 标识材料、观察、判断或传闻。物件不可到达时使用 `available: false`，并准备合理的失败路径。 |
| `evidence` | 可由玩家持有和出示的证物，关联调查主题 | 将隐藏证物设为 `initial: false`。获取规则由成功动作授权。 |
| `actions` | `ask` 联系角色，`inspect` 核查记录，`tell` 向其他角色透露信息 | 为每个动作列出有权角色、目标、主题、前置证物及必要成本。有需要时在 `grants` 列出成功后发给请求者的证物 ID。 |
| `reactions` | 按主题和角色配置的事件反应候选 | 反应同样使用动作许可和前置检查。拿同一份材料问不同角色，观察各自结果。 |
| `followups` | 玩家可追问的接收状态、内容与来源 | 只给作为参与者或获披露授权的视角。私人交流可因角色陈述变成新证词。 |

## 样例与复核

雾港案的 `inspect_audit_receipt` 是一条带前置条件的调查。本席玩家先给宋屿看编号有关联的半张过磅联，宋屿才有材料去审计组核查底单。`requires` 引用 `harbor_weight_slip`，`target` 指向 `audit_receipt`，成功时发放 `harbor_audit_receipt`。直接猜出证物 ID 的玩家应无法出示尚未持有的底单。

配置校验检查题面、引用、角色授权与证物的可达授予链。角色决策、拒绝和实际查找结果仍需拿完整场景验证。[配置校验](../api/npc_case_data.py)

提交新案之前，逐一复核这些情形。

- 两个角色面对同一主题时，至少有一处差异能从动机、关系、现有记录或权限解释。
- 能从一条玩家可见回报追到来源记录或有权转述的角色。口头主张在转述后仍标为主张。
- 新会话中的访客不会取得主玩家的私有任务、证物或角色聊天。显式分享只发布获准的内容。
- 玩家按真实线索可以选出正确对象和动机。缺少材料、猜错和访问失败后都有继续调查的步骤。
- 每条证据链至少有一条可反证的断言，例如私聊不出现在另一席位、前置证物缺失不能成功、同一任务恢复只结算一次。
- 模型选择可用预置候选复现，事实和结案结果在 Mock、Rules 和真实模型路径中一致。报告注明真实模型调用范围和预算。[系统与权限边界](ARCHITECTURE.md)
